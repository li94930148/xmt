# XMT v2.20.24 北京时间与活动日志保留

## 问题与根因

系统时间契约要求数据库保存北京时间民用时间、API 返回带 `+08:00` 的 ISO-8601 时间。活动日志的既有写入遗漏 `created_at`，实际使用 SQLite `CURRENT_TIMESTAMP` 写入 UTC；日志 API 又返回无偏移字符串，页面因此把 UTC 墙上时间误当北京时间。

## 改动范围

- migration 012 将来源明确的历史 `activity_log.created_at` 统一加 8 小时，并删除早于最近 7 天的日志。
- 所有当前活动日志写入点显式绑定北京时间，不再依赖表默认时间。
- `/api/users/logs` 与 `/api/users/activity-logs` 统一返回 `YYYY-MM-DDTHH:mm:ss+08:00`。
- 插入触发器以最新活动时间为基准持续清理 7 天前的日志；升级启动时先完成一次全量过期清理。
- 新增按用户、日期去重的 `user_login_days` 汇总，从清理前的历史登录日志回填并随新登录更新，使 7/30 天登录成就不依赖已过期的原始日志。
- 资料中心、日报归档、Social Review、Creator Center、协作时间线及日期排序/编辑回填统一通过共享北京时间层处理，不再依赖浏览器所在时区。
- 数据库兼容层把运行时 DML 中遗留的 `CURRENT_TIMESTAMP` 和单一 `datetime('now', '+8 hours')` 绑定为同一北京时间参数；按周、按日和在线状态查询补齐北京时间偏移。

## 数据与兼容边界

- migration 012 会永久删除 7 天前的 `activity_log`；这是本版本明确的数据保留规则。仅保留不含操作详情的每日登录汇总供连续登录成就使用。
- 不删除 Session、Refresh Token、Auth Event、选题历史、创作历史、消息或其他业务表。
- 历史活动日志可安全校正，因为当前仓库中所有旧写入路径都省略 `created_at`，来源明确为 SQLite UTC 默认值；不对来源不明的其他时间字段做全库平移。

## 验证

- 活动日志专项测试覆盖 UTC 历史值校正、7 天边界、插入后持续清理及 `+08:00` API 序列化。
- 时间合同测试覆盖运行时 `CURRENT_TIMESTAMP` 的北京时间参数绑定。
- 类型检查、版本一致性和生产构建纳入发布闭环。
