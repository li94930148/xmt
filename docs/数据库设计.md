# 数据库设计

## 文档说明

本文档基于以下两类真实来源整理：

1. 当前项目实际数据库文件 `data/xmt.db`
2. 当前数据库初始化与运行时迁移脚本 `api/database/db.ts`

本文档目的不是虚构理想模型，而是明确：

1. 当前真实已落地的数据结构
2. 当前仍处于兼容或过渡状态的结构
3. 后续品牌化与平台化需要重点治理的方向

## 数据库总览

当前数据库已覆盖以下业务域：

1. 用户与权限
2. 内容生产主流程
3. 协作与消息
4. 工作流与模板
5. 运营与辅助模块
6. 抖音数据
7. 系统元数据
8. 历史兼容结构

当前数据库已经具备中台型产品雏形，不再只是单表驱动的小型业务库。

## 当前兼容或过渡结构

### `editing`

当前数据库和初始化脚本中都存在 `editing` 表。

当前判断：

1. 该表属于历史兼容结构
2. 仍需保留以兼容现有数据
3. 但它不是当前前端主路径的核心模块

后续建议：

1. 核查实际使用链路
2. 明确是保留兼容、迁移替代，还是归档停用

## 真实结构与治理重点

### 已确认的特点

1. 数据库以主流程链路为中心扩展
2. 权限、协作、运营模块已进入正式结构
3. 部分业务关系仍依赖应用层维护
4. 迁移方式当前仍偏运行时增量修补

### 当前需要特别关注的问题

1. 数据库初始化脚本与长期运行数据库需要持续核对
2. 历史表、兼容表、主路径表需要明确边界
3. 平台化前必须建立更稳定的迁移管理方式

## 品牌中台阶段的数据库方向

在“自有品牌中台”阶段，数据库需要重点支持：

1. 系统品牌配置
2. 多团队/多业务线预留
3. 更稳定的模板能力
4. 更清晰的工作流与通知联动

这意味着数据库未来会更强调：

1. 配置化
2. 可演进
3. 可复制
4. 可治理

## 行业通用平台阶段的数据库方向

未来如果向行业通用平台扩展，数据库应逐步具备以下能力：

1. 多组织模型
2. 多空间/多项目模型
3. 行业模板模型
4. 系统配置与品牌配置模型
5. 更稳定的统计与审计模型

## 后续治理建议

### 已明确建议

1. 建立正式迁移机制，不再只依赖运行时补字段
2. 核查 `editing` 等历史兼容结构的去留策略
3. 持续保持数据库文档与真实结构同步
4. 为品牌化和平台化能力预留统一配置模型

### 当前结论

当前数据库已经具备做成品牌中台的基础，但距离做成可复制的行业通用系统，还需要先完成：

1. 结构稳定化
2. 迁移规范化
3. 历史结构治理
4. 配置能力模型化

## 内容字段语义说明

P1-002D-6 后，内容生产主流程中的编辑器字段需要按当前真实保存行为理解。当前项目仍以 HTML string 作为主要内容格式，不应把 Markdown / JSON 兼容字段视为可靠 canonical 数据源。

### topics

1. `description`：选题描述字段，可承载选题说明、项目背景、目标受众等描述信息。
2. `outline`：选题大纲 / 剧本大纲字段，可作为 Production 初始 `content` 的来源。
3. `outline_markdown`：当前不应视为可靠 canonical Markdown；运行时可能由 `outline` 兜底写入，实际内容可能仍是 HTML。
4. `outline_json`：当前不应视为可靠 canonical JSON；运行时可能由 `outline` 兜底写入，实际内容可能仍是 HTML。

### production

1. `content`：当前唯一可靠的创作正文主字段，前端编辑器主要以 HTML string 写入该字段。
2. `content_markdown`：当前不应视为可靠 canonical Markdown；前端未形成稳定 Markdown 提交链路，后端可能以 `content` 兜底写入。
3. `content_json`：当前不应视为可靠 canonical JSON；前端未形成稳定 JSON 提交链路，后端可能以 `content` 兜底写入。
4. `version`：当前版本号，例如 `v1.0`。
5. `status`：创作状态，例如 `draft`、`review`、`approved`、`rejected`。

### production_history

1. `production_history` 主要保存 major / minor 版本保存前的旧快照。
2. 主要字段包括 `content`、`content_markdown`、`content_json`、`version`、`status`、`change_type`、`operator_id`。
3. 当前 history 保存的是更新前内容，不是更新后内容。
4. 当前 history 不完整覆盖所有审核提交行为。
5. 提交审核当前可能保存 Production 内容，但不生成 `production_history`。
6. 后续如需严格审计，应单独设计“审核快照”或更完整的版本策略。

### workflow_document_versions

Migration 029 通过 SAFE_EXPAND 新增独立版本快照表，供选题大纲、拍摄剧本和发布文稿保存显式小版本或大版本。

1. `document_type`：仅允许 `topic_outline`、`shooting_script`、`publishing_script`。
2. `document_id`：对应选题、拍摄或发布记录 ID，以文本形式保存。
3. `version` 与 `content`：显式版本号及保存时的正文快照；文档类型、记录 ID 和版本号组合唯一。
4. `change_type` 与 `is_baseline`：显式小版本、大版本或首次建立历史时保留的基线快照。
5. `operator_id` 与 `created_at`：显式版本的操作人和北京时间；历史身份未知时不补猜，基线两项均为 NULL。
6. `source_production_id` 与 `source_production_version`：可选来源创作记录和版本，不是当前正文源。
7. 此表是只读历史，不替代 `topics.outline`、`shooting.script_content` 或 `publishing.script_content`；普通保存不自动生成版本。
8. 删除选题、拍摄或发布记录时，在同一事务清理相应快照；迁移不回填旧版本，也不修改现存正文。

### shooting

1. `script_content`：拍摄阶段本地剧本内容。
2. 当 `script_content` 为空时，页面可能 fallback 到 latest approved Production 内容。
3. 保存 Shooting 剧本后只写 `shooting.script_content`。
4. Shooting 保存不回写 Production。

### publishing

1. `script_content`：发布阶段本地内容。
2. 当 `script_content` 为空时，页面可能 fallback 到 Production 内容或当前代码中的既有来源。
3. 保存 Publishing 内容后只写 `publishing.script_content`。
4. Publishing 保存不回写 Shooting，也不回写 Production。

### 当前内容字段风险

1. `content_markdown` / `content_json` 当前不可靠，可能仍保存 HTML。
2. `outline_markdown` / `outline_json` 当前不可靠，可能仍保存 HTML。
3. 当前阶段还没有严格“阶段快照”模型。
4. Shooting / Publishing fallback 可能读取 latest approved Production，而不是固定版本快照。
5. 批注 / 评论仍存在多套概念：旧编辑器内联批注、Tiptap mark、后端 `comments` 表。

## Workflow Engine 观测数据

当前 Workflow Engine 已新增独立观测表 `workflow_shadow_logs`，用于记录 workflow policy / decision 运行时的影子日志。

### workflow_shadow_logs

字段语义：

1. `id`：日志 ID。
2. `topic_id`：关联选题。
3. `node_id`：关联审批节点。
4. `from_state`：审批发生时的来源状态。
5. `to_state`：节点目标状态。
6. `user_id`：触发审批的用户。
7. `action`：引擎模式与动作，例如 `v2_strict:approved` 或 `v2_strict:blocked:approved`。
8. `reason`：policy / decision 输出原因。
9. `created_at`：记录时间。

当前定位：

1. `workflow_shadow_logs` 是观测与决策辅助表，不替代 `approval_records`。
2. 当前没有修改 `approval_records` schema。
3. 当前 strict gate 的阻断原因会 fallback 写入 `workflow_shadow_logs`。
4. Analytics 与 Decision API 均基于该表做只读聚合。

当前风险：

1. shadow logs 是行为观测数据，不应作为唯一审批审计来源。
2. strict 模式会基于 policy / decision 阻断部分审批，但不改变主业务表结构。
3. 后续如需要完整审计闭环，可再评估是否把 decision metadata 正式写入 `approval_records`。

## Workflow Engine v2 数据边界

P1-003E 完成后，`workflow_shadow_logs` 已成为 Workflow Engine v2 的核心观测层，但它仍不是业务主状态表，也不是 event sourcing 事件流。

### 当前定位

1. `workflow_shadow_logs` 用于记录 shadow、decision、partial control 和 strict gate 的运行上下文。
2. strict 模式下，policy / decision 阻断原因会 fallback 写入 `workflow_shadow_logs`。
3. Analytics、Decision、WorkflowDesigner 风险提示均可读取该表形成辅助判断。
4. 该表不替代 `approval_records`，也不替代 topic / workflow template 的真实业务状态。

### approval_records 当前状态

1. 当前尚未进入 `approval_records` policy 字段结构化阶段。
2. 当前未新增 `policy_checked`、`policy_mode`、`transition_allowed`、`approve_allowed` 等结构化字段。
3. 如后续需要完整审批审计闭环，应单独评估 schema 变更和历史数据兼容策略。

### 非 event sourcing 说明

当前系统仍是 HTML / 状态 / 事件驱动模型，不是 event sourcing：

1. `workflow_shadow_logs` 不能完整回放业务状态。
2. `workflow_shadow_logs` 不能作为唯一审批审计来源。
3. `topic.status`、workflow templates、approval runtime 仍由现有业务表和接口语义决定。
4. Strict Enforcement 是执行前 gate，不是数据库事件溯源引擎。

## 协作状态说明

本次实时协作编辑能力不修改数据库结构。

1. `production.content` 仍是创作管理正文最终落库字段。
2. `shooting.script_content` 仍是成片制作剧本最终落库字段。
3. Yjs 文档增量、在线用户、光标、选区、typing 状态均为 runtime state。
4. 协作状态不入库，仅存在 Socket.IO / Yjs 运行时内存中。
5. 房间无人在线后，运行时协作文档状态可被销毁；持久化恢复依赖现有业务字段。
