# 日报系统前端设计

## 权限与只读状态

- 个人日报读取保持登录 + 本人范围；`canCreate` 依据当前 `report:daily:submit` 权限返回。前端必须同时等待权限读取和接口能力确认后才开放填写/提交，不按角色名称推断能力。
- 无提交权限时，已有日报正文只读，并说明联系管理员开通权限；没有记录时说明当前没有日报及填写权限。日报提交 API 的守卫仍是最终授权边界。
- 团队页签/请求依据 `report:daily:view_team`；未授权直达 `/daily-report/team` 显示原因和返回个人日报操作，不请求团队数据。日报归档依据 `report:daily:archive` 或本人提交权限，不通过 `director` 角色名称绕过接口守卫。
- 报告中心只展示权限允许的日报入口。个人月报/年报仍采用既有登录 + 本人范围的服务端规则，不套用日报提交权限；月报/年报团队归档规则另由总结 API 判定。

## 草稿保存与提交的部分成功恢复

- 桌面日报的“提交”包含先保存草稿、再正式提交两个独立服务端写入阶段。
- 草稿保存成功后必须立即将服务端返回的日报 ID、版本和内容写入页面状态；不能等正式提交成功后才更新。
- 若正式提交失败，页面说明草稿已保存但尚未提交，保留该日报和最新版本供安全重试；不要退回旧版本、清空内容或新建重复日报。
- 正式提交失败时，页面内的持续提示承担错误说明和重试引导，不再叠加会在重试成功后残留的全局失败通知；成功后只展示成功反馈。
- 保存草稿与正式提交共用同步提交锁；提交期间正文与刷新暂时禁用，避免重复写入以及迟到响应覆盖等待期间的输入。失败后恢复编辑与重试。
- 若提交请求报错且无法确认服务端是否已提交，必须先用只读日报查询核对当前状态：已提交时提示成功；仍为草稿/退回时保留内容并允许检查后重试；读取也失败或状态缺失时锁定编辑和再次提交，只提供只读核实入口。已提交、已审核、已归档等非草稿/退回状态不可编辑或再次提交。
- 个人日报异步读取和提交结果回读必须绑定发起时的账号身份；切换账号后，旧账号的迟到成功/失败响应不得写入新账号页面。
- 月报/年报读取期间及提交期间，填写字段与年份/月别选择暂时禁用；提交使用同步锁防止快速重复请求。失败解锁并保留原文，用户可核对后明确重试。
- 浏览器回归需覆盖草稿保存成功、提交失败、页面保留记录/版本、同一日报重试、提交响应丢失但服务端已提交、状态核实失败后只读恢复、账号切换迟到响应，以及写入次数与状态；本机夹具不代替真实账号验收。

## 页面结构

- `/daily-report` 使用三个 Tab：我的日报、团队日报、总结归档。
- 普通用户显示“我的日报”和“总结归档”。
- 具备 `report:daily:view_team` 的用户显示“团队日报”；管理员沿用现有权限通配，不以编导等角色名称代替具体权限。

## 组件结构

- `DailyReportPage.tsx`：页面状态、接口编排、Tab 切换。
- `DailyReportComposer.tsx`：个人日报填写、保存草稿、提交。
- `DailyReportAutoSummaryPanel.tsx`：自动草稿建议展示和追加。
- `DailyReportTeamBoard.tsx`：团队日报列表与审核入口。
- `DailyReportSummaryArchive.tsx`：当前总结归档 Tab，查询和展示日报/月报/年报。
- `DailyReportArchiveList.tsx`：遗留归档展示组件，当前页面未挂载。
- `DailyReportReviewDialog.tsx`：通过/退回审核弹窗。
- `DailyReportStatusPill.tsx`：状态和风险标签。
- `dailyReportStatusLabel.ts`：日报归档、状态徽标共享的中文状态映射；未知或缺失状态显示“状态待确认”。

日报归档中草稿、已提交、已审核、已退回和已归档必须分别展示，不得把非草稿一律归为已提交，也不得把未知状态猜成草稿。当前总结归档标签页以 `DailyReportSummaryArchive.tsx` 展示日报/月报/年报。
